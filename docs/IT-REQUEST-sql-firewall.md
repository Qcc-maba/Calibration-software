# בקשה ל-IT — הפורטל והמערכת לא מגיעים ל-SQL אחרי שינוי ה-Security Group

הודעה מוכנה לשליחה. הרקע הטכני שמתחתיה נועד לענות על שאלות המשך, לא לשליחה.

## המייל

**אל: סלבה**
**נושא: השינוי ב-Security Group חסם גם את האפליקציה — cal ו-stg בלי נתונים**

היי סלבה,

השינוי שעשית אתמול ב-Security Group של MbaCustWeb בשביל פורטל הלקוחות סגר בטעות גם את הדרך
שבה **המערכת עצמה** מגיעה למסד. מאתמול `cal.qcc.co.il` ו-`stg.qcc.co.il` עולים, נראים תקינים,
וכל מסך שמושך נתונים חוזר ריק — בשתי הסביבות.

**למה זה קרה — הנקודה שקל לפספס:**
האתר לא רץ אצלנו בשרת. הוא רץ ב-Vercel, והקוד שלו מתחבר ל-SQL ב-`51.17.121.203:1433`
**מתוך AWS באזור us-east-1 (וירג'יניה)** — לא מכתובת של המשרד. אז כשמצמצמים את 1433 לכתובות
מוכרות, המשרד ממשיך לעבוד (ולכן מבפנים הכול נראה תקין) אבל האפליקציה נחסמת.

**איך אני יודע שזו הרשת ולא באג אצלנו:**

- מהמשרד: אותה שאילתה, אותו connection string — **0.4 שניות**, מחזירה נתונים.
- מ-Vercel: **timeout אחרי 10.0 שניות בדיוק**, שוב ושוב, בשתי הסביבות.
- `Test-NetConnection 51.17.121.203 -Port 1433` **מחוץ למשרד** — נכשל. מתוך המשרד — עובד.
- סיסמה שגויה או שירות שנפל היו מחזירים שגיאה **מיידית**. עשר שניות של שתיקה זה חבילות
  שנזרקות, כלומר סינון ברמת הרשת.

**מה אני מבקש — להשאיר את ההידוק שעשית, ולהוסיף נתיב אחד מוגדר:**

| | |
|---|---|
| שרת | MbaCustWeb (`51.17.121.203`, פנימי `172.31.34.165`) |
| כלל | Inbound, TCP, port **1433** |
| מקור | הכתובת שממנה Vercel יוצא — ראה שתי האפשרויות |
| לא לגעת | הכלל הקיים ל-`31.168.173.90/32` (המשרד) — עובד ונחוץ |

**שתי אפשרויות, לפי סדר עדיפות:**

1. **הנכונה:** אני מפעיל ב-Vercel **Secure Compute**, שנותן לפרויקט **כתובת יציאה קבועה**.
   אתה מוסיף כלל `/32` אחד, בדיוק כמו של המשרד — וזה לא יישבר שוב בשינוי הבא. אני צריך יום
   כדי להפעיל ולהעביר לך את הכתובת.
2. **זמנית, אם צריך את המערכת באוויר לפני זה:** פתיחה רחבה יותר של 1433.
   שים לב ש"להוסיף את הטווחים של Vercel" הוא לא פתרון מעשי — הפונקציות רצות ב-us-east-1,
   שזה מאות בלוקי CIDR, הרבה מעבר למכסת 60 הכללים של Security Group. אז בפועל האפשרות
   הזמנית היא פתיחה רחבה, ואני מעדיף שלא נשאיר אותה: במסד יושבים נתוני לקוחות, ו-1433 חשוף
   לאינטרנט נסרק תוך שעות. אם בכל זאת — רק יחד עם `sa` מנוטרל, סיסמאות חזקות ל-`app_prod`
   ו-`app_stage`, `Force Encryption` דלוק, ותאריך יעד לסגירה.

**עוד בקשה קטנה:** תוכל להסתכל ב-CloudTrail על `RevokeSecurityGroupIngress` מ-08/09 באותו SG?
זה יראה בדיוק איזה כלל הוסר ומה היה בו, ואז אפשר להחזיר בדיוק את מה שהיה במקום להמציא חדש.

`{"database":"ok"}` תוך פחות משנייה — הנתיב פתוח והמערכת חזרה.

## הרקע הטכני (לא לשליחה)

### מה נמדד

| בדיקה | תוצאה |
|---|---|
| `stg.qcc.co.il/api/health/db` | `{"database":"unreachable","ms":10198,"name":"PrismaClientInitializationError"}` |
| `cal.qcc.co.il` — כל קריאת נתונים | 500 אחרי 10.5 שניות |
| אותה שאילתה מהמשרד (pyodbc ו-Prisma) | 0.4–0.6 שניות, מחזירה נתונים |
| `Test-NetConnection 51.17.121.203 -Port 1433` מחוץ למשרד | נכשל |
| אותה בדיקה מתוך המשרד | `TcpTestSucceeded : True` |
| `CONNECTIONPROPERTY('client_net_address')` | `31.168.173.90` — השרת רואה את המשרד ככתובת ציבורית אחת |

### למה זה בהכרח רשת ולא קוד או הרשאות

- **סיסמה שגויה או לוגין נעול** → השרת עונה ודוחה **מיד**. כאן יש 10 שניות שתיקה.
- **השירות נפל / הפורט סגור ברמת ה-OS** → `RST` מיידי. גם לא זה.
- **10.0 שניות קבועות, חוזרות** → זה ה-connect timeout של Prisma. חבילות שנזרקות (`DROP`), שזו בדיוק ההתנהגות של Security Group שלא מתיר את המקור.
- אותו קוד, אותו connection string, אותו Prisma client — **עובד מהמכונה שלי**. ההבדל היחיד הוא מאיפה החיבור יוצא.

### איפה הפונקציות של Vercel באמת רצות

מכותרת התגובה של שני האתרים:

```
X-Vercel-Id: fra1::iad1::9668h-...
```

`fra1` הוא ה-PoP שקיבל את הבקשה (פרנקפורט); **`iad1` הוא האזור שבו הפונקציה רצה — AWS us-east-1**. כלומר החיבור ל-1433 יוצא מטווחי AWS של וירג'יניה.

לכן "להוסיף את טווחי Vercel" הוא לא פתרון מעשי בלי Secure Compute: מדובר במאות CIDR-ים של us-east-1, הרבה מעבר למכסת הכללים של Security Group (60 כברירת מחדל).

### הכיוון הארוך

הפתרון שלא דורש לחשוף 1433 לאינטרנט בכלל: שהאפליקציה תדבר **HTTPS** מול שירות בתוך ה-VPC, והוא ידבר עם ה-SQL פנימית — בדיוק הדפוס של `CustomerPortalApi` שכבר קיים. לחלופין העברת המסד ל-RDS עם VPC peering.

### מה לבקש מ-CloudTrail

`RevokeSecurityGroupIngress` / `AuthorizeSecurityGroupIngress` מ-08/09/2026 על ה-SG של MbaCustWeb — יראה בדיוק איזה כלל הוסר ומה היה בו, כך שאפשר להחזיר בדיוק אותו במקום להמציא חדש.
