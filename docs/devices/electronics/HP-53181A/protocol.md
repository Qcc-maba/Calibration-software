# HP 53181A — פרוטוקול

מונה תדר, SCPI 1992.0, GPIB.

> **סטטוס: אומת מקצה לקצה מול החומרה — 2026-09-02.**
> זוהה, נתפס ע"י ה-BLCore, ולולאת המדידה רצה עם השומר פעיל.

## זיהוי

- **תשובת `*IDN?` בפועל:**
  ```
  HEWLETT-PACKARD,53181A,0,3703
  ```
- **`*OPT?`** → `0,030`
- **SN שנקבע:** `53181A`
- **מחלקת BL:** `Systems/Hydra-Group/ComServer/ComServerBL/Device/Hp53181aBL.cs`
- **BLCore:** `Systems/Hydra-Group/ComServer/ComServerBL/BLCore/Hp53181aBLCore.cs`
- **עזרי פענוח:** `Device/Hp53181aReadings.cs`

### ⚠️ התנגשות עם ה-34401A — הסיבה שהזיהוי לפי דגם

המונה מדווח `HEWLETT-PACKARD` — **בדיוק כמו המודד 34401A**. הענף הקיים ב-`handlePacket` חתך
`Substring(0, 15)`, שהוא `HEWLETT-PACKARD` לשני המכשירים גם יחד, ו-`Agilent34401aBLCore` תופס לפי
הטוקן `"HEWLETT"`. בלי טיפול, המונה היה:

- מקבל את ה-SN של המודד,
- נתפס ע"י ה-BL של המודד ומקבל פקודות `CONF:VOLT:DC`,
- ומתנגש איתו במילון ה-SN של `BaseBLCore` אילו שניהם היו על השולחן.

לכן נוסף ענף **לפני** ענף `HEWLETT`, שמזהה `53181A` ונותן לו SN משלו. ההתנהגות של ה-34401A לא
השתנתה כלל.

## פרוטוקול — עובד ומאומת

| פקודה | תשובה |
|---|---|
| `*IDN?` | `HEWLETT-PACKARD,53181A,0,3703` |
| `*OPT?` | `0,030` |
| `:SYST:ERR?` | `+0,"No error"` |
| `:SYST:VERS?` | `1992.0` |
| `:FUNC?` | `"FREQ"` |
| `:INP:IMP?` | `+1.00000E+006` (1 MΩ) |
| `:INP:COUP?` | `AC` |
| `:MEAS:VOLT:MAX? (@1)` | `+0.0E-001` — **עונה תוך ~600ms תמיד** |
| `:MEAS:FREQ? (@1)` / `:READ?` / `:INIT;:FETC?` | **נחסם בלי אות** |

### אותה מלכודת כמו ב-CNT-90

בלי אות בכניסה, מדידת תדר **נתקעת** ולא מחזירה כלום (נמדד: אין תשובה גם אחרי 10 שניות). מדידת מתח
עונה מהר בכל מצב, ולכן ה-BL שואל אותה קודם וניגש לשאילתת התדר רק אם יש אות
(`Hp53181aReadings.IndicatesSignalPresent`, סף 50mV). זה בדיוק הדפוס של `Cnt90BL`.

**בשונה מה-CNT-90 יש לו תור שגיאות SCPI אמיתי** — `:SYST:ERR?` עונה `+0,"No error"` — כך שאפשר
באמת לבדוק אם פקודה התקבלה.

### רצף האתחול

| # | פקודה | למה |
|---|-------|-----|
| 0 | `*RST` | מצב ידוע: `FUNC "FREQ"`, כניסה 1MΩ AC, arming מיידי |
| 1 | `*CLS` | ניקוי סטטוס ותור שגיאות |
| 2 | `:CONF:FREQ (@n)` | הכנת המדידה |

### לולאת המדידה

`:MEAS:VOLT:MAX? (@n)` (שומר) → ואם יש אות → `:MEAS:FREQ? (@n)`.

> `?` אינו בסוף הפקודה (`:MEAS:FREQ? (@1)`). זיהוי שאילתה ב-`GpibCom` תוקן ל-`IsQuery` בזמן
> העבודה על ה-CNT-90, ולכן המכשיר הזה עבד מהרגע הראשון.

## הגדרות

`Settings/HydraBL_Settings.json`, מפתח `Hp53181a`:

```json
"Hp53181a": {
  "Channels": [ 1 ],
  "MaxNumOfChannels": 2,
  "Masters": [],
  "Sensor": { "MeasureType": 7, "SensType": -1 }
}
```

`MeasureType: 7` = `Frequency` → היחידה המשודרת `Hertz`. ערוץ 1 הוא כניסת 225MHz; ערוץ 2 הוא
הכניסה האופציונלית לתדר גבוה.

## ⚠️ באג תשתית שהתגלה בזכות המכשיר הזה — קרא לפני דיבוג של "מכשיר לא עולה"

הבאתו של ה-53181A חשפה שני פגמים ב-`ServerCore` שהיו בלתי-נראים לחלוטין:

1. **טיקים של ה-device timer רצו במקביל.** `System.Timers.Timer` יורה כל 2 שניות בלי קשר לשאלה אם
   הטיק הקודם הסתיים, ו-`_TempDeviceHost` הוא **שדה משותף** שכל טיק מנקה בתחילתו וקורא בסופו. טיק
   אחד הכניס מכשיר מזוהה לתור הקידום, טיק אחר ניקה את הרשימה לפניו — והמכשיר נכנס לתור לנצח ומעולם
   לא קודם, **בלי אף שורת לוג ובלי חריגה**. תוקן עם שומר `Interlocked` שמדלג על טיק חופף.

2. **שלושה מסלולי כשל היו אילמים לגמרי:**
   - מכשיר ממתין שהקישור שלו סגור — הוסר בלי הודעה
   - מכשיר מזוהה שאף BL לא תבע — **נותק בלי הודעה** (זה מה שקורה כשה-`DeviceIdToken` לא תואם או
     שהמודול חסר מ-`ComServerSettings.Modules`)
   - שלב הקידום כולו היה עטוף ב-`catch { }` ריק

   כולם מדווחים עכשיו.

### ועוד ממצא פתוח: tunnel של GPIB למכשיר שאינו על האפיק תוקע את הכול

עם ה-CNT-90 (כתובת 7) וה-Datron (18) מנותקים, הטיק **נתקע** אחרי שגיאת `ENOL` על כתובת 7 ולעולם לא
מגיע לשלב הקידום — כלומר **מכשיר אחד חסר מרעיב את כל השאר**. אומת: הסרת שני ה-tunnels האלה גרמה
ל-53181A לעלות מיידית.

**מסקנה מעשית:** אל תשאיר tunnel של GPIB למכשיר שאינו מחובר.
**התיקון הנכון** (עדיין לא בוצע): לחסום את פעולות ה-GPIB ב-`GpibCom` כך ששגיאת אפיק לא תוכל לתקוע
את הלוח המשותף, או לדלג על tunnel שכשל בזיהוי פעמים רצופות.
